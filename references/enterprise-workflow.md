# 企业级处理流程与质量门禁

把每次歌谱工作当作一个可追踪的资料处理项目，而不是一次性聊天回答。除非用户明确只要简短结论，否则保留以下最小审计信息：输入文件路径、SHA-256、处理时间、技能版本、操作者/模型、输出状态和未解决问题。

## 阶段与停止条件

### G0：接收与范围

- 明确任务类型：`transcribe`（转写）、`analyze`（分析）、`arrange`（编曲）、`create`（原创）、`curate`（选歌/歌单）或 `batch`（批量）。
- 记录来源范围、目标受众、交付格式、是否允许使用/改写现成歌词，以及是否要求只在本地处理。
- 若来源、授权或目标格式缺失，先标记为 `blocked` 或 `needs-input`，不要用猜测推进到出版级输出。

### G1：来源登记与视觉核对

- 对每张图片登记相对路径、文件名、扩展名、大小、哈希和可见曲号/歌名；同号不同文件不要静默覆盖。
- 运行 `scripts/audit_images.py` 检查图片头、尺寸、文件尾标记和疑似截断；审计结果是警告，不代替人工查看清晰度。
- 先看原图，再使用 OCR 或脚本做辅助；OCR 结果只能作为候选，不是证据。
- 每一个曲目字段都应能回指来源文件；多页曲目要记录页序。

### G2：音乐与歌词转写

- 保留 `raw_transcription`（尽量贴近原图）和 `normalized_transcription`（统一空格、标点、段落）两份内容；任何修订写入 `change_log`。
- 以小节为最小核对单元，记录拍号、节拍总量、歌词字/音符对应、重复和终止。
- 符号看不清时使用 `uncertain_items`，包括原文位置、候选读法、置信度和需要人工复核的原因。

### G3：音乐、语言与神学审阅

- 音乐：核查音域、节拍、句法、重复、终止、会众可唱性与编曲假设。
- 语言：核查字词、断句、普通话重音、歌词与音符的对齐；不要为了押韵改变神学含义。
- 神学：区分经文原意、教会常用表达、作者观点和祷告愿望；不把愿望写成无条件应许，不伪造经文出处。
- 创作任务必须通过“独立性检查”：不得复用样本中可识别的连续歌词或旋律片段。

### G4：交付与发布

- 交付前给出状态：`draft`、`review`、`approved`、`rejected` 或 `needs-input`，并说明门禁结果。
- 分析/转写交付至少包含 Markdown 可读版和机器可读记录（JSON）；批量任务还要包含 manifest、错误清单和汇总统计。
- 机器记录使用字段级置信度、原始/标准化转写、质量问题、审核人和审核决定，并记录技能版本、任务模式和 ISO 8601 处理时间；Schema 变更必须递增 `schema_version`。
- 任何“正式谱面、出版、公开发布、录音定稿”的措辞都必须由用户明确要求并经过人工复核；默认只交付草稿或分析稿。

## 置信度与错误等级

- `high`：原图清晰，字段由两次视觉核对或原图与 OCR 交叉确认。
- `medium`：大部分可确认，仍有一个局部符号或歌词字需要人工确认。
- `low`：依赖模糊扫描、推断或不完整页；不得自动进入 `approved`。

问题等级：`P0`（身份/调号/关键旋律错误）、`P1`（节拍或歌词对齐错误）、`P2`（局部标记或排版问题）、`P3`（建议性优化）。P0/P1 未关闭时，状态不能为 `approved`。

## 批量与恢复

- 批量任务先运行 `scripts/catalog_hymns.py` 生成 manifest，再按稳定排序分批处理；不要一次把全部图片加载到上下文。
- 每个曲目单独保存记录；重复运行按哈希跳过未变化文件，哈希变化则新建版本并保留旧记录。
- 单曲失败不应让整批失败；写入 `errors.jsonl`，包含路径、阶段、错误等级、可重试性和下一步。
